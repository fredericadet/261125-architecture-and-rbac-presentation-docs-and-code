01 · CONCEPT

Qu'est-ce que le RBAC ?

Role-Based Access Control : les privilèges ne vont jamais directement à un utilisateur

Le principe

Les privilèges (SELECT, INSERT, CREATE…) sont accordés à des rôles, pas à des utilisateurs. Les utilisateurs reçoivent des rôles, les rôles s'empilent en hiérarchie.

Pourquoi

Révoquer ou accorder l'accès devient un simple changement de rôle, auditable. L'accès se gouverne indépendamment du turnover des utilisateurs.

Règle d'or n°1

Ne jamais accorder un privilège objet directement à un rôle fonctionnel. Toujours passer par un rôle d'accès intermédiaire.

Règle d'or n°2

Séparer qui administre les objets (SYSADMIN) de qui gouverne les accès (rôle RBAC ou SECURITYADMIN).

03 · DEUX TYPES DE RÔLES

Account Roles vs Database Roles

Ne pas confondre les deux objets Snowflake

Account Role

Visible dans tout le compte. Assignable à un utilisateur ou à un autre rôle. C'est le seul type de rôle que SCIM peut provisionner.

Database Role

Limité à une base précise : ne voit jamais en dehors. Ne peut pas être assigné directement à un utilisateur, ni posséder d'objets cross-base (vues, tâches…).

Les rôles d'accès aux schémas et bases (DB_R, TEST_SCHEMA_R…) sont des Database Roles. Les personas (DEV_ANALYST_RO…) sont des Account Roles.

04 · ARCHITECTURE

La hiérarchie complète à 6 couches

Toutes les organisations n'ont pas besoin de toutes les couches

1. Rôles natifs (OOB)

2. Admins d'environnement (DEV / PRD)

3. Admins de domaine métier

4. Admins de Data Product

5. Database Access Roles (DB_R / DB_RW / DB_C)

6. Schema Access Roles (schema_R / _RW / _C)

Couches en couleur : utilisées dans notre jeu de test (1, 2, 5 et 6). Pas de domaine métier ni de data product, non nécessaires pour un périmètre de test.

06 · COUCHE 5

Database Access Roles

DB_R / DB_RW / DB_C : un point d'entrée unique par base

LECTURE

DB_R

Agrège tous les <schema>_R de la base. Aucun privilège direct, uniquement de l'agrégation.

LECTURE / ÉCRITURE

DB_RW

Agrège tous les <schema>_RW. Hérite de DB_R.

CRÉATION

DB_C

Agrège tous les <schema>_C. Hérite de DB_RW. Donne le droit de CREATE, jamais l'ownership.

Pourquoi ? Sans cela, chaque nouveau schéma obligerait à regranter individuellement tous les consommateurs de la base.

07 · COUCHE 6

Schema Access Roles et MANAGED ACCESS

Là où vivent les vrais privilèges SQL

•TEST_SCHEMA_R : SELECT sur toutes les tables et vues, actuelles et futures (GRANT ... ON FUTURE).

•TEST_SCHEMA_RW : INSERT/UPDATE/DELETE, hérite de _R.

•TEST_SCHEMA_C : CREATE TABLE/VIEW/..., hérite de _RW, mais ne possède jamais les objets créés.

CREATE SCHEMA IF NOT EXISTS TEST_SCHEMA WITH MANAGED ACCESS;

MANAGED ACCESS est obligatoire : sans cette option, le créateur d'un objet peut accorder l'accès à sa guise et contourner toute la gouvernance mise en place.

10 · PIÈGES À ÉVITER

Les erreurs les plus fréquentes

Granter directement des privilèges objet à un rôle fonctionnel : perd toute refactorabilité.

Oublier MANAGED ACCESS sur un schéma : les créateurs d'objets contournent la gouvernance.

Oublier les grants FUTURE : les nouveaux objets n'héritent d'aucun droit.

Confondre ownership et usage : posséder un rôle (GRANT OWNERSHIP ON ROLE) ne le rend pas activable par un utilisateur.

Laisser ACCOUNTADMIN posséder des objets : toujours transférer vers SYSADMIN ou un admin délégué.

Rattacher SCIM à une Database Role : impossible techniquement, seuls les Account Roles sont assignables.

12 · INDUSTRIALISATION

4 pistes d'automatisation

Terraform

Provider officiel snowflake-labs/snowflake : rôles, grants et hiérarchie déclarés en code, versionnés, diffables (terraform plan) avant application.

Native App

Packager le pattern RBAC en Snowflake Native App : installation en un clic côté consommateur, logique de setup encapsulée et versionnée.

Lot de scripts GitHub

Dépôt de scripts SQL / Python paramétrables (par domaine, environnement), exécutés via CI/CD (GitHub Actions + Snowflake CLI) à chaque pull request.

DCM Snowflake

Database Change Management natif : définir rôles et grants dans un manifest.yml déclaratif, déployé et suivi directement par Snowflake.

Les quatre approches sont complémentaires : Terraform et DCM pour déclarer l'état cible, GitHub pour l'historique et la revue de code, Native App pour distribuer le pattern packagé à d'autres comptes.
